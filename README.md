## Предметная область

Компания поставляет электричество жилым домам и учитывает показания двухтарифных счётчиков. Объектом учёта выступает квартира или нежилое помещение. У объекта есть собственник, счётчик, тариф и история ежедневных показаний. На основании месячного потребления формируется счёт.

Проект демонстрирует Slowly Changing Dimensions: смену ФИО по SCD 1, историю тарифов по SCD 2 и хранение текущего и предыдущего телефонов по SCD 3. Движки ClickHouse также применяются для замены ошибочных показаний и отмены установок счётчиков.

## Архитектура

```text
Клиент ──HTTP/JSON──> Spring Boot API ──HTTP/SQL──> ClickHouse
                              ▲
                              │ CSV
                      Java-генератор
```

`ApiController` принимает HTTP-запросы, `Input` проверяет параметры и JSON, `EnergosbytService` реализует сценарии и правила SCD. `ClickHouse` передаёт параметризованные запросы по HTTP. `ApiErrors` возвращает ошибки в едином JSON-формате. Java-генератор потоково создаёт CSV; команды подготовки схемы и загрузки используют тот же исполняемый JAR, что и API.

Сервис учебный и работает без авторизации, cookie, сессий и Redis. Изменения данных сериализуются внутри одного экземпляра приложения. ClickHouse не обеспечивает внешние ключи, поэтому API проверяет существование связанных сущностей перед вставкой.

Стек: Java 21, Spring Boot 3.5, Maven, Docker Compose и ClickHouse 26.7.

## Модель данных

Факты ссылаются на измерения недвижимости, собственников, тарифов и счётчиков.
Показания `day_kw` и `night_kw` — накопительные значения счётчиков; в счёте указано потребление за месяц.

| Таблица | Назначение | Движок | Сортировочный ключ | Партиционирование |
| --- | --- | --- | --- | --- |
| `dim_realty` | Объекты недвижимости | `MergeTree` | `id` | Нет |
| `dim_gauges` | Счётчики | `MergeTree` | `id` | Нет |
| `dim_tariffs` | Тарифы, SCD 2 | `ReplacingMergeTree(updated_at)` | `(id, valid_from)` | Нет |
| `dim_users` | Собственники, SCD 1 и SCD 3 | `ReplacingMergeTree(updated_at)` | `id` | Нет |
| `fact_gauge_bindings` | Установки и отмены счётчиков | `VersionedCollapsingMergeTree(sign, version)` | `(realty_id, gauge_id)` | Нет |
| `fact_meter_readings` | Ежедневные показания | `ReplacingMergeTree(created_at)` | `(realty_id, reading_date)` | По месяцу показания |
| `fact_invoice` | Счета | `MergeTree` | `(realty_id, created_at)` | По месяцу выставления |

### Обоснование ключей и партиционирования

- `dim_realty` и `dim_gauges`: ключ `id` соответствует поиску объекта и счётчика по идентификатору. Небольшие измерения хранятся в одной общей партиции, чтобы не создавать множество малых частей.
- `dim_users`: ключ `id` объединяет версии одного собственника. `updated_at` определяет актуальную строку, поэтому не входит в сортировочный ключ. Общая партиция сохраняет возможность слияния всех версий независимо от даты изменения.
- `dim_tariffs`: ключ `(id, valid_from)` сохраняет разные интервалы одного тарифа для SCD 2. При ключе только по `id` старые интервалы были бы потеряны при замещении. Исправления одного интервала выбираются по `updated_at`; все интервалы остаются в общей партиции небольшого измерения.
- `fact_gauge_bindings`: ключ `(realty_id, gauge_id)` группирует установки по объекту и прибору. Отмена повторяет ключ и версию исходной установки, а `sign` задаёт направление записи. Время установки не входит в ключ; партиционирования по времени нет, чтобы исходная строка и её поздняя отмена могли схлопнуться в одной партиции.
- `fact_meter_readings`: ключ `(realty_id, reading_date)` соответствует запросу показаний объекта за период и объединяет корректировки одной даты. Значения показаний и идентификатор счётчика не входят в ключ, поскольку могут корректироваться. `PARTITION BY toYYYYMM(reading_date)` ограничивает данные месяцем; неизменная дата гарантирует, что версии одного показания попадут в одну партицию.
- `fact_invoice`: ключ `(realty_id, created_at)` соответствует выборке счетов объекта с упорядочением по времени. Месячные партиции `toYYYYMM(created_at)` группируют счета по расчётным месяцам и позволяют обслуживать историю помесячно, не создавая отдельную партицию для каждого объекта или дня.

`ReplacingMergeTree` и `VersionedCollapsingMergeTree` выполняют слияния в фоне. В запросах, которым нужна актуальная версия, применяется `FINAL`; корректность API не зависит от предварительного `OPTIMIZE TABLE ... FINAL`. Для обычных таблиц `MergeTree` замещения строк нет.

### Генерируемые данные

`make gen` записывает в `data/` CSV в UTF-8 без заголовков. Генератор детерминирован и создаёт строки потоково.

| Таблица | Содержимое |
| --- | --- |
| `dim_realty` | 1 000 квартир и нежилых помещений в десяти домах |
| `dim_gauges` | 1 100 счётчиков |
| `dim_users` | 1 000 собственников |
| `dim_tariffs` | Три версии тарифа: с 2023-11-01, 2024-11-01 и 2026-11-01; последняя действует до 2099-01-01 |
| `fact_gauge_bindings` | 1 200 исходных строк; после схлопывания остаётся 1 000 активных установок, 100 из них — версии 2 |
| `fact_meter_readings` | Показания 1 000 объектов за каждый день с 2023-11-01 по 2026-10-31; 3% дат дополнены корректировкой |
| `fact_invoice` | По 36 счетов на объект; срок оплаты — 10-е число следующего месяца |

Первые 100 объектов получают новый счётчик 2025-05-01. Его накопительные показания начинаются заново, но месячное потребление учитывает показания до и после замены. Цена счёта рассчитывается по тарифу на дату выставления.

## HTTP API

Тела запросов и ответов — JSON. Имена полей используют `snake_case`; даты имеют формат `YYYY-MM-DD`, дата и время — `YYYY-MM-DD HH:MM:SS` в UTC. Ошибки возвращаются как `{"message":"..."}`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/ping` | Проверка доступности; ответ `200` с пустым телом |
| `GET` | `/users/{id}` | Получить собственника |
| `PATCH` | `/users/{id}` | Изменить `fio` и/или `phone`; ответ `204` |
| `GET` | `/realty/{id}` | Получить объект недвижимости |
| `POST` | `/realty/{id}/readings` | Передать или скорректировать показание; ответ `201` |
| `GET` | `/realty/{id}/readings?date_from=...&date_to=...` | Получить актуальные показания за включительный период |
| `GET` | `/realty/{id}/invoices?limit=10&offset=0` | Получить страницу счетов; сортировка по дате убыванию |
| `GET` | `/tariffs?date=2026-11-01` | Получить версию тарифа, действовавшую на дату |
| `POST` | `/realty/{id}/gauges` | Установить или заменить счётчик; ответ `201` |

В запросе показаний обязательны `user_id`, `gauge_id`, `tariff_id`, `reading_date`, `day_kw` и `night_kw`. Значения показаний должны быть целыми неотрицательными числами. При повторной передаче за одну дату старая строка сохраняется, а новая получает более поздний `created_at`.

В запросе изменения собственника поля `fio` и `phone` необязательны, но хотя бы одно нужно указать. При смене телефона прежний текущий телефон становится `phone_prev`. При замене счётчика активная установка аннулируется, затем добавляется новая с увеличенной версией.

Для отсутствующей сущности API возвращает `404` и `{"message":"Not found"}`; для неверного поля или параметра — `400`. Числа проверяются по диапазонам `UInt32` и `UInt64`.

### Пример запроса

```bash
curl -i http://localhost:8080/ping

curl -X POST http://localhost:8080/realty/1/readings \
  -H 'Content-Type: application/json' \
  -d '{"user_id":1,"gauge_id":1001,"tariff_id":1,"reading_date":"2026-10-01","day_kw":1250,"night_kw":300}'

curl 'http://localhost:8080/realty/1/readings?date_from=2026-10-01&date_to=2026-10-31'
```

Postman-коллекция со всеми эндпоинтами находится в [`api/Energosbyt.postman_collection.json`](api/Energosbyt.postman_collection.json). Порядок импорта и примеры PowerShell описаны в [`api/README.md`](api/README.md).

### Примеры SQL для SCD

Ниже приведены действия через HTTP, соответствующие SQL-проверки и ожидаемые результаты.
Примеры используют тестовые данные, созданные генератором; PATCH и POST изменяют эти данные.
Идентификаторы и прежнее ФИО в примерах соответствуют состоянию после первой загрузки. SQL выполняется в базе `energosbyt`.

Команда для подключения к ClickHouse:

```bash
docker compose --env-file .env.local exec clickhouse sh -c 'clickhouse-client --port "$CLICKHOUSE_PORT" --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" --database "$CLICKHOUSE_DATABASE"'
```

**SCD 1 — ФИО.** При передаче `PATCH /users/1` с `{"fio":"Петрова Анна Сергеевна"}` сервис синхронно меняет ФИО во всех доступных версиях собственника и добавляет актуальное состояние новой строкой. Последующий `GET /users/1` возвращает новое ФИО. Версионная колонка `updated_at` не меняется мутацией: для неё вычисляется новая версия при вставке.

SQL изменения ФИО, используемый сервисом, с подставленными значениями:

```sql
ALTER TABLE dim_users UPDATE fio='Петрова Анна Сергеевна'
WHERE id=1 SETTINGS mutations_sync=2;
```

После завершения HTTP-запроса новая версия содержит новое ФИО; проверка без `FINAL` подтверждает, что прежнее ФИО отсутствует во всех доступных строках собственника:

```sql
SELECT id, fio FROM dim_users WHERE id=1;
SELECT count() FROM dim_users WHERE id=1 AND fio='Собственник 1'; -- 0
```

**SCD 3 — телефон.** Рассмотрим два последовательных запроса `PATCH /users/1`: сначала с `{"phone":"+79111111111"}`, затем с `{"phone":"+79222222222"}`. При каждом изменении сервис читает актуальную строку через `FINAL`, переносит её `phone` в `phone_prev` и вставляет новую строку с более поздним `updated_at`, сохраняя исходный `created_at`. При повторной передаче того же телефона `phone_prev` не меняется.

```sql
SELECT id, phone, phone_prev FROM dim_users FINAL WHERE id=1;
-- phone = +79222222222, phone_prev = +79111111111
```

**SCD 2 — тариф.** Границы интервалов полуоткрытые: `valid_from <= date < valid_to`.

Запросы `GET /tariffs?date=2026-10-31` и `GET /tariffs?date=2026-11-01` возвращают разные версии: дневная цена меняется с 620 на 700 копеек, ночная — с 310 на 350. Версии уже включены в генератор. SQL ниже показывает сохранённые интервалы одного тарифа, включая закрытые; открытый интервал заканчивается `2099-01-01 00:00:00`.

```sql
SELECT id, price_day_kwph, price_night_kwph, valid_from, valid_to
FROM dim_tariffs FINAL WHERE id=1 ORDER BY valid_from;
```

Сумма исторического счёта проверяется по тарифу, действовавшему в дату выставления:

```sql
SELECT i.created_at, i.price,
       i.day_kw*t.price_day_kwph + i.night_kw*t.price_night_kwph AS recalculated
FROM fact_invoice i
INNER JOIN (SELECT * FROM dim_tariffs FINAL) t ON i.tariff_id=t.id
WHERE i.realty_id=1 AND i.created_at>=t.valid_from AND i.created_at<t.valid_to
ORDER BY i.created_at;
```

Для сгенерированных счетов `recalculated` совпадает с сохранённым `price`. JOIN выбирает тариф по дате исходного счёта, поэтому новый тариф не меняет цену старого месяца. Это проверочный пересчёт: запрос не обновляет строки `fact_invoice`.

**Корректировка показаний.** Запрос с `FINAL` возвращает последнюю версию за дату:

Рассмотрим повторную передачу показания из примера POST в разделе API за `2026-10-01`: в первом запросе `day_kw=1250`, во втором — `day_kw=1260`. Сервис вставляет новую строку с тем же ключом и `created_at` позже предыдущего; старую строку явно не удаляет. GET за эту дату и SQL ниже возвращают одну строку с `day_kw=1260` и `night_kw=300`, независимо от фоновых слияний.

```sql
SELECT * FROM fact_meter_readings FINAL
WHERE realty_id=1 AND reading_date='2026-10-01';
```

**Замена счётчика.** После установки нового счётчика активной остаётся одна запись:

При передаче `POST /realty/1/gauges` с `{"gauge_id":1100}` сервис одним INSERT добавляет отмену прежней установки со `sign=-1`, исходными ключом, `created_at` и `version`, затем новую установку со `sign=1` и увеличенной версией. При отсутствии активной установки первая версия равна 1.

```sql
SELECT * FROM fact_gauge_bindings FINAL WHERE realty_id=1;
```

В результате остаётся строка `gauge_id=1100`, `sign=1`. Для объекта №1 после первой загрузки данных новая версия равна 3: замена версии 2 уже сгенерирована. После повторных установок версия будет выше. Исходная установка и её отмена схлопываются; отдельной строки `sign=-1` после `FINAL` не требуется.

**Удаление ошибочной строки.** Пример использует отдельную тестовую запись и синхронную мутацию.

В примере используется `id=90000`, отсутствующий в данных генератора. Если такая запись уже существует, для примера потребуется другой свободный идентификатор. Сначала добавим запись с лишним нулём в площади и прочитаем её, затем удалим строку:

```sql
INSERT INTO dim_realty VALUES (90000,'Ошибочная запись',5000,'nrcp','',0,1,1,now());
SELECT id, square FROM dim_realty WHERE id=90000; -- square = 5000
ALTER TABLE dim_realty DELETE WHERE id=90000 SETTINGS mutations_sync=2;
SELECT count() FROM dim_realty WHERE id=90000; -- 0
```

`mutations_sync=2` ожидает завершения мутации, поэтому нулевое количество строк можно проверять сразу после DELETE.

## Запуск

Необходимы Docker Engine или Docker Desktop с Docker Compose 2.20 или новее и GNU Make. Java и Maven на хосте устанавливать не нужно: приложение и команды работы с данными запускаются в контейнерах. В Windows команды Makefile выполняются из Linux/WSL с доступом к Docker Desktop.

`docker-compose.yml` подключает определения сервисов из `compose.services.yml` через `include` и загружает `.env.local` для подстановки переменных. Поэтому команды `docker compose logs` и `docker compose down` работают без дополнительного `--env-file`; настройки по-прежнему хранятся только в `.env.local`.

Запускайте команды в корне проекта:

```bash
make run
make setup
curl -i http://localhost:8080/ping
make services
```

| Команда | Назначение |
| --- | --- |
| `make run` | Собрать приложение и запустить ClickHouse и API, дождаться готовности |
| `make stop` | Остановить контейнеры; локальное хранилище `volume/` сохраняется |
| `make gen` | Создать CSV в `data/` |
| `make load` | Загрузить CSV в пустые таблицы |
| `make setup` | Последовательно создать схему, сгенерировать и загрузить данные |
| `make teardown` | Удалить семь таблиц проекта вместе с данными в них |
| `make test` | Собрать Java-образ и выполнить модульные тесты Maven |

`make teardown` удаляет учебные таблицы ClickHouse, но сохраняет файлы CSV и папку хранилища. После очистки повторите `make setup`. Загрузчик заранее проверяет CSV и состояние таблиц; если таблицы непустые, загрузка прекращается до первого `INSERT`, чтобы предотвратить дубли.

Загрузка выполняется через HTTP с `INSERT INTO <таблица> FORMAT CSV`: Java-клиент передаёт файл потоком без загрузки целого датасета в память. После частично выполненной загрузки сначала требуется `make teardown`, затем `make setup`. Повторный `load` не продолжает частичную загрузку автоматически; иначе в таблице установок могли бы повториться отменяющие строки.

## Конфигурация

`.env.local` — единственный файл настроек проекта. Он хранится в репозитории и содержит учебные значения, не предназначенные для использования с реальными секретами.

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `APP_PORT` | Порт HTTP API | `8080` |
| `CLICKHOUSE_HOST` | Хост ClickHouse для обращений с компьютера | `localhost` |
| `CLICKHOUSE_PORT` | Нативный порт ClickHouse | `9000` |
| `CLICKHOUSE_HTTP_PORT` | HTTP-порт ClickHouse | `8123` |
| `CLICKHOUSE_USER` | Пользователь ClickHouse | `default` |
| `CLICKHOUSE_PASSWORD` | Пароль пользователя ClickHouse | см. `.env.local` |
| `CLICKHOUSE_DATABASE` | База данных | `energosbyt` |
| `CLICKHOUSE_IMAGE` | Образ ClickHouse | `clickhouse/clickhouse-server:26.7` |
| `MAVEN_IMAGE` | Образ для сборки и тестов | `maven:3.9.11-eclipse-temurin-21` |
| `JAVA_IMAGE` | Образ Java runtime | `eclipse-temurin:21-jre` |
| `TZ` | Часовой пояс контейнеров | `UTC` |

Из контейнера приложения ClickHouse доступен по имени сервиса `clickhouse`. Данные ClickHouse хранятся в `volume/`; CSV-датасеты — в `data/`. Эти каталоги исключены из Git.

## Тестирование

Модульные тесты запускаются при сборке приложения (`make run` или `make test`). `InputTest` проверяет валидацию чисел, идентификаторов, дат и пагинации. `DataGeneratorTest` проверяет воспроизводимость CSV, корректировки показаний, сроки оплаты счетов и замену счётчика.

`LiveScdTest` проверяет интеграцию с настоящим ClickHouse и API: объёмы загруженных данных, расчёты счетов, работу SCD и ответы на корректные и ошибочные запросы. Для его запуска API и ClickHouse должны быть запущены, а схема и данные подготовлены. Тест включает собственный набор записей с идентификаторами `90001` и `90002` и удаляет его после проверки.

```bash
docker build --target build \
  --build-arg MAVEN_IMAGE=maven:3.9.11-eclipse-temurin-21 \
  --build-arg JAVA_IMAGE=eclipse-temurin:21-jre \
  -t abds-lab-checks:local .

docker run --rm --network abds-lab_default --env-file .env.local \
  -e CLICKHOUSE_HOST=clickhouse \
  -e LAB_INTEGRATION_TEST=true \
  -e APP_BASE_URL=http://app:8080 \
  abds-lab-checks:local mvn -B -ntp -Dtest=LiveScdTest test
```

Если в `.env.local` изменён `APP_PORT`, укажите соответствующий порт в `APP_BASE_URL`. Для ручной проверки API также можно импортировать коллекцию Postman.
